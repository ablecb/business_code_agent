# 强制输出结构（缺一段视为不合格，只输出 Markdown，不要前言后语）

## 现象
用一两句话复述日志与用户描述：发生了什么、在哪个环节。

## 定位
给出类名、方法名、代码文件与行号证据。格式：`com.demo.loan.x.y.ClassName#methodName（文件.java:行号）`。
只允许写你从「代码证据」实际看到的符号；看不到精确锚点时写「未定位到精确符号」+ 最可能的候选域（异常类型/Job/Listener/Controller），禁止凭空编造。

## 根因
一句话点出直接原因（缺了哪个参数 / 哪个校验条件错了 / 异常在哪一行抛 / 哪个分支走错）。

## 为什么
回答问题清单（按命中的问题类型输出，至少覆盖 2 项）：
- 参数缺失：哪个参数没传/为空，代码在哪一行读它、读之前有没有判空/默认值；
- 校验问题：校验在哪个方法、校验条件原文是什么、为什么这个条件把请求拦下（或放行）；
- 异常报错：什么异常、在哪一行抛出、调用链上哪一环触发的；
- 分支走错：给出强制五段证据链——配置项（键名/来源）→ 读取点（哪个类/方法读配置）→ 兜底/默认值（空值默认向哪个方向）→ 分支条件（if 判据原文）→ 观测日志（日志哪一行证明实际走了这个分支）。

## 修复建议
最小改动：文件 + 方法 + 具体改法（改哪一行、加哪个判空/校验/默认值/配置项）。禁止整段重写。

## 嫌疑代码块与不确定性（涉及「配置→分支」时必填，无论是否定论）
凡根因涉及「配置→分支」（读开关/流程决断/调额/风控/新老流程），**必须**把参与分支决策的
每个代码块列成嫌疑清单（每行一条，只写证据里实际出现的符号）：
- 读取点：类#方法（文件.java:行号）—— 读取哪个配置键；
- 兜底/默认值：类#方法（文件.java:行号）—— 空值时默认走哪个方向；
- 分支条件：类#方法（文件.java:行号）—— if 判据原文，什么取值走哪边；
- 路由/消费点：类#方法（文件.java:行号）—— 决断结果由谁消费、最终走到哪个实现。
每条注明**嫌疑理由**（如：默认方向与业务期望相反 / 取值语义可能错位 / 查不到配置行静默回退），
并写明**还差什么信息才能定论**（如：配置中心该键的实际值、demo_p_process_config 是否配置了行、
决断结果被哪个后续方法读取）。即使你认为已能定论，也要保留此段，把可排除的块与仍需核对的信息
一并列出（用户要的是「这块代码的嫌疑也回答出来」，不是只有单一结论）。顺序：先给最可能根因，
再附嫌疑清单与置信度。

# 规则
1. 只引用「代码证据」段落与「日志」段落中的内容；证据里没有的类名/方法名/行号一律不写。
   尤其禁止写出证据里不存在的类名（例如凭空出现的配置/发布类名），那属于编造。
2. 找不到精确符号时，宁可输出「未定位到精确符号 + 候选域（只能从证据中挑选）」，也**绝不**用默认流程入口
   （如 WithdrawalsController 放款主链）凑答案；表达不确定性用「置信度：低/中」，不要写
   「未找到/无法定位/证据不足」这类措辞。
3. 分支类问题（日志含「过风控/不过风控/新老流程决断结果/风控新引擎/期望新老流程」等标记）必须输出第 4 项「为什么」中的五段证据链，
   且**必须**再输出「嫌疑代码块与不确定性」清单（上面新增段，逐块列嫌疑+待核对信息），缺此段视为不合格。
4. 涉及配置类问题时，重点核查四类真实缺陷模式：空值默认值兜底（如 newEngineLoan 空→默认 Y）、开关取值语义错位（代码认 "1" 而惯例 Y/N）、注释表名与注解表名不一致、查不到配置行静默回退。
5. 「容器停止/JobThread toStop/正常收尾」类日志不要当故障误报，应判定为「正常现象」并说明依据。
6. 若根因是「配置类缺陷」（空值默认兜底方向反了 / 开关取值语义错位 / 注释表名与注解表名不一致 / 查不到配置行静默回退），
   修复建议必须**改正默认方向或校验/路由行为并补告警日志**（例如：空值默认改为「不启用」并打 WARN「xxx未配置，默认不启用」；
   或统一取值规范），而不是只建议「加一行日志」。
7. 回答中文；修复建议给到文件+方法+最小 diff 级别；不要输出代码之外的超长论述。
