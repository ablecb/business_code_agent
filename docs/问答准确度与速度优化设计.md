# 问答准确度与速度优化设计（只读方案，不包含实现）

> 目标：在**不牺牲准确度**的前提下降低单轮问答延迟，或让同样的延迟换来更高准确度。
> 适用代码基线：当前工作区（`app/agent/graph_agent.py`、`app/agent/explore_agent.py`、
> `app/agent/ask_retrieval.py`、`app/tagging/search.py`、`app/analysis/golden_qa.py`、
> `app/agent/session_store.py` 等）。本文件只给出设计与验收方式，不改代码。

---

## 0. 结论

可以同时提升，但前提是分清两类杠杆：

- **双赢杠杆**：同一个改动让"更准"和"更快"同时发生（缓存复用、证据继承、入口锁定、
  离线快路径扩覆盖、黄金问答库扩覆盖）。这类是首选。
- **此消彼长杠杆**：加深下钻、调大 max_tokens/温度、每轮必跑 LLM 评审——准确换延迟，
  只应在双赢杠杆用尽后按场景取舍。

单轮 ask 的延迟构成（已从代码确认）：

```
意图识别 LLM (graph_agent._understand)
  + 研究计划 LLM (task_planner.build_research_plan_async)
  + 探索工具循环 LLM × 4~12 轮 (explore_agent.run_explore_agent，每轮一次)
  + 总结 LLM (explore_agent._summarize_from_evidence / graph_agent._reply)
  + 评审 LLM (answer_reviewer / _finish_with_review)
  ≈ 8~16 次串行 LLM 调用 → 延迟主体在此
```

检索层（Milvus 1 次 + MySQL LIKE + Neo4j 1 次）本身远快于 LLM，但存在
**每问重复 embedding、重复 SQL 扫描、追问重复读码**等可缓存浪费。

---

## 1. 先量化，再优化（基线测量）

任何优化前先建立基线，避免"感觉变快了"的误判：

1. **现成指标**：`ChatResponse.elapsed_ms`（每次对话返回）、`explore_steps`
   （每步工具与命中）、`/api/v1/chat/{session_id}/trajectory`（完整事件流）。
2. **脚本基线**：`scripts/eval_expanded_battery.py`、`scripts/loan_qa_smoke.py`
   已能批量跑问答集并打印 `llm=… explore_backend=… milvus=…` 环境信息。
3. **建议采集**（改造前先跑一轮）：
   - 平均/中位 `elapsed_ms`；
   - 平均探索轮数（`len(explore_steps)`）；
   - 每轮 LLM 调用次数（trajectory 里按 `type=step` + `step_id` 统计）；
   - 黄金问答命中率、FOLLOWS 快路径命中率（相关 step note 里已有 `golden_qa` /
     `offline_fast_path` 标记）。
4. 优化后同一问题集回跑，对比以上四项；**只有当轮数↓ 或 命中率↑ 且答案质量未降
   （幻觉检测/人工抽检）才算双赢达标**。

## 2. 双赢杠杆设计（推荐优先实施）

### 2.1 检索缓存层（embedding + hybrid_search）

**现状**：`hybrid_search`（`app/tagging/search.py:195`）每次调用都
`get_embedding_provider().embed_one(q)`（`search.py:210`）再查 Milvus；
随后对每个字面词做多条 LIKE（`search.py:334-401`）。追问短句（≤40 字）常与上轮
问题高度重叠，却全部重算。代码中**没有任何问答级缓存**（`app/llm/factory.py`
只有 provider 的 `lru_cache`，无响应缓存）。

**设计**：

- 新增 `app/tagging/search_cache.py`：进程内 LRU（`OrderedDict` + 容量上限，约 512
  条；单进程服务足够，不必引入 Redis）：
  - `cached_embed(text) -> list[float]`：按 `text`（可再叠加 `provider+model` 前缀）
    缓存 embedding 结果；
  - `cached_hybrid_search(q, project_id, top_k, domain) -> list[SymbolHit]`：键为
    `(project_id, q, top_k, domain)`。命中直接返回；未命中调 `hybrid_search` 后写入。
- **缓存窗口只在"当前问题"**：所有写入的 key 用当前 `q`（问题原词+keywords 拼接后的
  检索串 `graph_agent._retrieve` 的 `q_parts`）；**不要缓存"问题+扩展词"的变体**，避免
  语义漂移。（可选增强：追问短句时用 `(prior_question, q)` 双键命中，直接复用上轮
  retrieved 集合——见 2.2 证据继承。）
- 失效策略：`ingest` 完成后清空（`full_refresh`/增量完成后调 `search_cache.clear()`），
  避免索引更新后命中旧证据；单条 TTL 不做，进程 LRU 足够。

**收益**：追问/相似问直接跳过 embedding+Milvus+MySQL（省 100~500ms 检索 + 一次
embedding API）；结果与上轮一致 → 口径稳定。**双赢**。

**验收**：同一会话连续两问（短追问），trajectory 中第二轮 `milvus_search` 步骤
耗时≈0；`search_cache` 命中计数上升；答案质量抽检不降。

### 2.2 会话证据继承（追问不重复读码）

**现状**：`session_store.update_context`（`app/agent/session_store.py:108`）只保存
`last_entry`/`explore_steps` 等指针性字段；下一轮探索（`explore_agent.run_explore_agent`）
即使 `resolve_session_ctx_gate` 判为 dig_in/followup，仍是**从零开始** search→读码，
已读过的源码不在上下文里（`_optimization 方案.md` 3.3 已提出 `evidence_seen`，未实现）。

**设计**：

1. `session_store` 增加：
   - `record_evidence(session_id, evidence_pack)`：把本轮 `retrieved` 的
     `(fqcn, method_name, kind, summary/raw_code 摘要)` 追加进 `ctx["evidence_seen"]`
     （上限 20 条，按 `fqcn#method_name` 去重）；
   - `get_evidence_context(session_id) -> str`：渲染成"已读证据"文本块。
2. `graph_agent._explore`（`graph_agent.py:1471`）在构造 `entry_hint`/`question` 时，
   若 `use_session_ctx=True`（追问），把 `get_evidence_context` 追加进传给
   `run_explore_agent` 的提示；`explore_agent` 相应侧（`_read_method_names`、
   `_pending_same_class_helpers`，`explore_agent.py:3226/3258` 已有"已读集合"雏形）
   改为优先复用已读摘要，提示语改为"以上代码已在上一轮读过，禁止重复 get_symbol_code"。
3. 与 2.1 结合：追问轮直接复用上轮 `retrieved` 作为初始 evidence，探索轮数可
   **平均减少 3~6 轮**（省 3~6 次 LLM 调用 = 秒级延迟）。

**收益**：快（少串行 LLM 往返）；准（已读证据摘要进上下文，防止换一轮就编造/口径
漂移，也解决"上一答说错了让你重查"时仍然基于同一包证据重答的稳定性）。**双赢**。

**验收**：多轮追问测试集（`tests/test_ask_retrieval.py` 已有部分），对比第二轮起
`explore_steps` 明显变短且答案含已读类名。

### 2.3 黄金问答库扩覆盖（命中=免长链）

**现状**：`app/analysis/golden_qa.py:651 try_golden_answer` 已作为 `graph_agent`
`_dispatch_by_intent` 快路径（`graph_agent.py:2920`），`golden_qa_enabled=True`、
`golden_qa_min_score=0.55`。生成脚本 `scripts/generate_golden_qa.py` 已存在。

**设计**（扩覆盖而非改命中逻辑）：

1. **自动回填**：对"人工确认回答正确"的会话（已有 `/chat/feedback` upsert，
   `app/api/chat.py:187`），把该 (问, 答) 对写入 `golden_qa` 预检表，作为候选；
   由校验脚本（相似度 + 抽检）过滤后入库。
2. **低频高命中阈值校准**：对追问/重复问（同一 session 两次出现相似 `q`），短命中
   阈值可放宽（0.55 → 0.45），因为答案来自用户已接受的上一轮。
3. **不扩的场景护栏**：保持现有排除——add-api 脚手架、compose_code 故事、
   endpoint/URL 问（`graph_agent.py:3027-3036`）不进黄金，避免表关系式答案抢答。

**收益**：命中即免 8~16 次 LLM 链（**快**），答案来自离线高置信对（**准**），且是
README 已声明的内网 qwen3 准确率兜底方案。**双赢**。

**验收**：跑 `scripts/generate_golden_qa.py` 后，用 `scripts/eval_expanded_battery.py`
统计 golden 命中率上升、平均 `elapsed_ms` 下降。

### 2.4 FOLLOWS / 离线快路径触发放宽

**现状**：`explore_agent._eligible_follows_spine_fast_path`（`explore_agent.py:2512`）
只在特定问题型（sync-first、完整流程、状态流转等）命中 `_load_follows_spine_flow`
（`explore_agent.py:2550`）后直接按入库业务摘要作答，跳过工具循环。

**设计**：维持现有判定函数不变，扩大两处：
- 从 `question` 判定扩展到**会话内已有锁定入口**（`last_class_method`）+ 追问型
  （dig_in/followup）也走该快路径，答案基于已入库的 entry FlowDoc；
- source-only 模式下已存在此 bypass（`explore_agent.py:4393-4453`），确认 index
  模式下同样开闸。

**收益**：流程类问题平均少 5~8 轮工具循环（**快**）；答案直接来自 ingest 期 AI 固化
的业务摘要，比现场 LLM 现编链路更贴源码（**准**）。**双赢**。

**验收**：流程问句（"xx流程什么样"）`explore_steps` 仅含 `offline_fast_path` 步骤；
对比改动前后答案中类名/落库事实无漂移。

### 2.5 入口锁定质量（选对入口=少走弯路）

**现状**：入口锁定链路已较多层：`_understand` 的 `entry_hint` → `_retrieve` 的
Controller 优先（`graph_agent.py:232-266`）→ `ask_retrieval.prefer_flow_entry`
（`ask_retrieval.py:989`）→ `explore_agent._resolve_flow_entry_anchor` +
`_entry_aligned_with_question`（`explore_agent.py:403/294`）。

**设计**（小改、不重排优先级）：
- 在 `prefer_flow_entry` 返回空时，用 `_lexical_main_entry(question)`（用户原话里的
  `XxxController#method` / 类名）作为**最终兜底锁定**，并让 `explore_agent` 的
  `_entry_aligned_with_question` 对"兜底锁定"放行（现行为是 mismatch 就清空
  `entry_hint`，导致少一轮仍要重新 search 定位）。
- 目的：**保证每轮都带一个入口开跑**（省 1~2 轮定位），同时把"入口与问题不匹配"的
  拒绝逻辑从清空改为"降级为 lexical 候选"（不牺牲防漂移）。

**收益**：快（省定位轮）；准（入口即证据锚点，防换入口）。**双赢**。

**验收**：对"XX服务地址是什么"等 endpoint 问，第一步即 `get_symbol_code` 命中目标
Client，而非先 search 2 轮。

### 2.6 LLM 流式输出（感知延迟，不影响准确）

**现状**：`/api/v1/chat/stream` 已是 SSE（`app/api/chat.py:114`），但所有
`llm.chat(...)` 调用均不带 stream（`优化方案.md` 6.2 亦指出）。最终答案是一整块
`final` 事件才到 UI。

**设计**：
- 先看 provider 实现（`app/llm/` 各 provider 是否已支持 `stream` 参数——若不支持，
  此条降级为"先在 UI 展示 step/intent 事件"——本项目已做到，故此项优先级可放 P2）。
- 若支持：`graph_agent._reply`/`_summarize_from_evidence` 的调用加 `stream=True`，
  经 `chat/stream` 逐 chunk 转发 `type=chunk` 事件。

**收益**：感知首字延迟大幅下降。**速度（感知）**；不影响（不牺牲）准确。

**验收**：SSE 流里出现 `type=chunk` 且早于 `final`；无 chunk 时回退原样（fail-open）。

## 4. 可选加项（成本更高，收益次之）

1. **短问双键召回**：追问（≤40 字）时用 `(prior_question, q)` 合并召回（类似
   `ask_retrieval.py:2264-2281` 已有先例），与 2.1/2.2 合并为一个"追问快捷通道"。
2. **检索精排**：`_rerank_hits_for_question`（`explore_agent.py:390`）之后，对 top 12
   再做一次小 LLM 精排（仅流程/改动类问题，1 次调用）；准确↑、延迟+1 次调用——属于
   "用 1 次 LLM 换检索质量"的取舍项。
3. **PEV 管线调用精简**：`agent_use_pev=True`（`config.py:114`）时顺序 QA
   （`graph_agent._run_sequential_qa`，`graph_agent.py:3149`）每节点都跑
   `run_pev_pipeline`；对纯 ask 节点可直接走 2.2 证据继承复用，避免重复计划。

## 5. 实施顺序与回滚

**P0（推荐先做，双赢）**
1. 2.1 检索缓存层（独立新文件，不动管线）
2. 2.2 会话证据继承（`session_store` + `graph_agent._explore` + `explore_agent` 提示）
3. 2.3 黄金问答库回填脚本与阈值校准

**P1**
4. 2.4 FOLLOWS 快路径扩展（判定函数触发放宽）
5. 2.5 入口兜底锁定

**P2**
6. 2.6 流式输出；3.并行工具/评审降频（若基线显示轮数是主导延迟）；4.1 追问双键。

**回滚**：每项做成开关（`config.py` 新增布尔，默认 true；出问题置 false 立即复原），
缓存类给 `clear()` 挂到 ingest 后，证据继承类给 `ctx["evidence_seen"]` 空值即退化回
现状。

## 6. 风险清单

- 缓存旧证据 → ingest 后未清空：在 `ingest` 完成回调挂 `search_cache.clear()` + 版本号
  进缓存键（`project_id` 后附 `ingest_seq`）。
- 证据继承导致"锁定太死"（新话题误继承）：沿用 `resolve_session_ctx_gate` 的
  `new_topic` 判定，`new_topic=True` 时跳过证据注入（`graph_agent.py:1539` 已有
  `turn_stage_isolated` 先例）。
- 黄金问答误命中：维持现有护栏 + 回填前人工/规则抽检。
- 流式 chunk 与最终 `final` 一致性：chunk 仅作预览，`final` 仍为权威正文，避免
  前端拼接误差。

---

## 7. 一句话总结

**优先做"缓存复用 + 证据继承 + 黄金/离线快路径扩覆盖"四个双赢点**：它们把单轮
8~16 次串行 LLM 调用压缩到 3~6 次（快），同时让每轮都基于已入库事实/已读证据作答
（准）；再按基线数据决定是否动用"并行工具、评审降频、流式"等取舍项。
