# 内网部署指南（Ollama + qwen3:32b）

本指南面向**纯内网环境**：无外网 API（siliconflow/deepseek 均不可用），LLM 走内网
Ollama 上的 GGUF 模型（如 `qwen3:32b`，即 `4Q_K_M` 量化格式）。

## 1. 架构总览

```
浏览器 / Electron 客户端
        │  HTTP
        ▼
FastAPI (app/main.py) ──┬── LLM ──────────────► Ollama (http://<内网IP>:11434)
                        │                        ├─ qwen3:32b      （对话）
                        │                        └─ bge-m3         （向量）
                        ├── MySQL  ── 符号/标签字典（内网 MySQL 或 Docker）
                        ├── Neo4j  ── 调用图（可选，无则流程题降级）
                        └── Milvus ── 向量库（MILVUS_MODE=lite 本地文件，无需 Docker）
```

## 2. Ollama 部署（内网服务器）

```bash
# Linux 服务器（内网离线安装时，从有网机器下载 rpm/deb 拷贝过去）
curl -fsSL https://ollama.com/install.sh | sh

# 拉取模型（需要一次外网，或从有网机器 ollama pull 后 export/import）
ollama pull qwen3:32b
ollama pull bge-m3          # 向量模型，qwen3 没有 embedding 能力

# 监听内网地址（供其他机器访问）
# 修改 systemd 服务或设环境变量：
export OLLAMA_HOST=0.0.0.0:11434
ollama serve
```

**离线迁移模型**（内网无外网时）：
```bash
# 有网机器上：
ollama pull qwen3:32b
ollama pull bge-m3
ollama show qwen3:32b --modelfile > qwen3.modelfile   # 记录 tag/量化
# 拷贝 ~/.ollama/models/blobs 目录到内网机器同名位置，或：
# ollama create 内网自定义名 --file modelfile（如你的 4Q_K_M 自定义量化）
```

## 3. 一键切换 .env

```bash
python scripts/switch_ollama.py                # 预览将改动的键
python scripts/switch_ollama.py --apply        # 实际写入 .env（自动备份原文件）
# 自定义地址/模型：
python scripts/switch_ollama.py --apply --host http://192.0.2.100:11434 --model qwen3:32b --embed-model bge-m3
# 恢复外网配置：
python scripts/switch_ollama.py --restore
```

切换后 `.env` 关键值：

| 变量 | 值 | 说明 |
|---|---|---|
| `LLM_PROVIDER` | `ollama` | 已有 provider 支持 |
| `LLM_MODEL` | `qwen3:32b` | 你的 GGUF tag |
| `LLM_BASE_URL` | `http://127.0.0.1:11434` | 内网地址可写 IP |
| `EMBEDDING_PROVIDER` | `openai_compatible` | 走 Ollama `/v1/embeddings` |
| `EMBEDDING_MODEL` | `bge-m3` | 1024 维；nomic-embed-text 为 768 维 |
| `EMBEDDING_BASE_URL` | `http://127.0.0.1:11434/v1` | 补 `/v1` 由代码自动处理 |
| `EMBEDDING_DIM` | `1024` | 与向量模型一致 |
| `MILVUS_MODE` | `lite` | 无 Docker 时本地文件库 |

## 4. 向量库：Milvus lite（免 Docker）

`MILVUS_MODE=lite` 时数据落在 `data/milvus_demo.db`，不依赖 etcd/minio/milvus 容器。

> ⚠️ **切换 embedding 维度后必须删除旧库重新 ingest**：
> ```bash
> del data\milvus_demo.db
> python scripts/run_ingest.py --full-refresh
> ```

## 6. 内网模型的已知限制与建议

- **qwen3-32B(Q4) 长链工具调用稳定性一般**：Agent 每轮输出 JSON 工具调用，
  建议 `LLM_TEMPERATURE=0.2`（已在示例默认）、`LLM_ENABLE_THINKING=false`（打标签更快）。
- **embedding 质量决定"精确给代码"的检索效果**：bge-m3 中英混合好于 nomic；
  若内网无任何向量模型，可临时 `EMBEDDING_PROVIDER=hash` 兜底（精度明显下降）。
- **MySQL/Neo4j 内网化**：docker-compose.yml 可整体搬到内网服务器
  （`docker compose up -d`），或对接内网既有实例，改 `.env` 的 `MYSQL_*` / `NEO4J_*`。
- **首次全量 ingest 耗时较长**（解析 + 打标签 + 建图 + 向量），可分段
  `python scripts/run_ingest.py` 观察日志。

## 7. 关键：用黄金问答库把准确率拉回来（qwen3 专用，推荐）

**为什么需要**：内网只有 qwen3-32b 时，让它在线做 DSH/Cursor 式长链工具推理
（自主翻代码 → 规划 → 验证）准确率会明显下降——这是 32B 模型的能力上限，
不是配置问题。**方案：把重推理搬到离线。**

**原理**：ingest 后用当前 LLM（思考模式 + 自一致性投票）把项目咀嚼成高置信
问答对，存 MySQL `golden_qa` 表；运行时 chat 对 ask 类问题先检索该库，
命中高分直接返回存储答案 —— qwen3 在线只做检索/组装，不做长链推理。

```bash
# 1) 先确保已 ingest（生成 FlowDoc 业务叙事等索引材料）
python scripts/run_ingest.py --full-refresh

# 2) 预览候选问题（不调用模型）
python scripts/generate_golden_qa.py --dry-run

# 3) 表结构字典 + 表关联黄金问答（确定性，不耗模型，秒级完成）
python scripts/generate_golden_qa.py --table-dict-only

# 4) 离线生成（脚本自动强制 LLM_ENABLE_THINKING=true，qwen3 思考模式质量更高）
python scripts/generate_golden_qa.py --project demo-loan --limit 300

# 5) 看库存
python scripts/generate_golden_qa.py --stats
```

**表结构字典（`app/analysis/table_dict.py`）**：
- 离线扫描全部 Entity（`@TableName` + 字段注释 + `@ApiModel`/类 javadoc/Controller `@Api` tags
  推导中文表名），落 MySQL `table_dict` 表；
- 自动推导「表关联」（同名字段 + 关联键语义，每对表保留最优键）→ 生成确定性黄金问答
  （`source=table_relation`）：「A表和B表怎么关联的」命中即答 `t1.orderId = t2.orderId`，
  不经过 LLM，运行时零推理；
- 重建会先清旧的关系黄金行再重插（`--table-dict-only` 可反复跑）。

生成行为：
- 候选来源：FlowDoc 流程入口（每题 2 问：完整流程 / 入口做什么）+ Controller
  关键方法（每题 1 问）+ **表结构字典推导的表关联**（确定性答案，无需 LLM）；
- 每题采样 `GOLDEN_QA_N_SAMPLES`（默认 3）份答案，用 embedding 两两相似度
  取「最居中」的一份（self-consistency 投票），`votes` 记录一致度；
- 重复运行跳过已有问题（`--overwrite` 强制重生成）。

入口问法（「XX入口在哪个 Controller」「调用了哪些下游接口」）：PEV goal 契约
已加确定性护栏，强制按 explain_flow 解析入口（entry_route 实测可解析这些问法
→ DemoWithdrawalsController#withdrawals），不再误判成 inventory 返回「未找到」。

## 8.5 代码生成（写方法 / 给段代码）

用户要「写个方法 / 给段代码 / 开发个功能」时走常规 explore/PEV 管线：
- 判定：`写/给我/帮我写/开发/实现/生成 + 方法|代码|函数|SQL|类`（排除加字段/贴源码/解释）；
- 流程：检索项目真实实现（grep/read/PEV 证据链）→ 用真实标识符按项目风格作答，
  Request/Response 包装、异常处理、日志风格与项目一致；
- 找不到证据必须明说「未在项目中找到…」，禁止编造类名/字段。
实测示例「给我一个方法查机构中心的报文取字段」→ 生成代码与
`DemoOrganizationServiceImpl.queryProductAccModuleDetail` 同风格，命中真实
`ApiOrgServiceClientParamDecorator` / `Response` / `SUCC_CODE` / `body.get("C")`。

## 8.6 通用兜底（意图×来源匹配）

- **意图×来源匹配**（`golden_qa._intent_source_bonus`）：问「字段/表结构」只让
  字段黄金加分，问「关联/关系」只让关联黄金加分，问「流程」略偏 consensus——
  防止字段问答与关联问答互相抢答；
- **表字段黄金**（`--table-dict-only` 一并生成）：每张表生成「X表有哪些字段」
  确定性答案（`source=table_field`），字段列表问题命中即答；
- 引擎输出与现有快路径并行（golden/PEV 仍是捷径），跑稳后再评估收编。

## 8.7 修改能力（改代码 / 加字段 / 优化并验证）

用户要「改代码」时走**清单 + 落地闭环**（`_run_implement_pipeline`，桌面端在本机应用）：

- **流程**：先出修改清单（`patches`，含路径与替换段）→ 桌面端确认后由客户端
  在**本机**逐字应用（copy-on-write / `AGENT_WRITE_MODE`）→ 需要自测时编译验证
  → 失败把编译器错误回喂修复（`DEFAULT_MAX_REPAIRS` 次）；
- **护栏**：仅允许写入清单内文件（`locked_file_allowlist`），禁止扩改；
- **环境识别**：mvn 私有依赖缺失等环境错误不进入修复循环，如实报告
  （`env_blocked`），避免白修。

## 8.8 路由去正则化（capability 统一分类）

**改动**：把散落的 6 个正则路由分类器（通用问答/代码生成/修改/验证/入口判定）合并进
意图 LLM 的 `capability` 字段——一次调用同时输出 intent + capability
（`general|code_qa|codegen|modify|verify|meta`），`_dispatch_by_intent` 按 capability 分流；
正则降级为 `_heuristic_capability`（合并后的单一兜底函数，仅 LLM 失败时用）。

**收益**：
- 英文/换语言问句由 LLM 语义判定（实测 "What is the loan disbursement flow?" →
  code_qa → 查代码回答，不再被中文正则误判成通用闲聊）；
- codegen/modify 不进黄金快路径（golden 只对 code_qa 生效，避免「写个方法」被字段黄金抢答）；
- 新增场景 = 给 INTENT_PROMPT 加 capability 枚举与示例，不再加正则。

**保留的正则及原因**（这些不是路由，是闸门/评分，保持确定性）：
- 安全闸门：路径越界校验、工具 JSON 解析、verify 触发词（`wants_verify_action` 防止
  「写个快速排序」误入编译循环）；
- 数据层评分：golden 检索的 token/表名同现/意图×来源加权（只影响排序，不决定路径）；
- 窄兜底：PEV 入口问法护栏（针对 goal LLM 误判 inventory 的特定失败模式）。

## 9. 后续：接 DeepSeek Harness 做 Cursor 式问答（可选）
- **通用问题兜底**：非代码域问题（知识问答/闲聊/通用技术概念）不进入工具循环，
  直接由 LLM 回答（`GENERAL_FALLBACK_ENABLED=true`），保证任何问题都有回复。

质量建议：
- 生成时用**内网最强可用的模型**（一次外网 API 蒸馏质量最高；只有 qwen3-32b
  时靠多采样投票 + 思考模式挽回）；
- `GOLDEN_QA_MIN_SCORE` 调低 → 命中更多但可能答非所问；调高 → 更保守。
- 上线前用 `scripts/eval_qa.py` 回归，把常见问题补进候选（或直接手插
  `golden_qa` 表，`source='manual'`）。

## 8. 处理管线（单一管线）

统一走「黄金问答库 → explore/PEV → 通用直答」单一管线，不再有引擎选择：
web/desktop 前端不再提供「自动 / 本管线 / Harness」切换控件，请求与响应也不再
携带 `engine` / `engine_path` 字段。

| 环节 | 行为 |
|---|---|
| 黄金问答库 | 代码域纯问答命中即答（`golden_qa` 表） |
| explore/PEV | 未命中 → 检索 + PEV 证据链作答，改动类问题给清单与 CTA |
| 通用兜底 | 非代码问题直接 LLM 回答，保证任何问题都有回复 |
