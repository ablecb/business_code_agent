## 4. 测试设计要点（由浅入深）

### L1 浅层：CST 解析与变量类型
- 用真实 Java 源码片段直接喂 tree-sitter，断言 `extract_method_locals` 对
  参数/`new`/`cast`/`foreach`/`catch`/赋值重填的类型推断。
- 关键设计：**first declaration wins** —— `kind = "FIXED"` 重赋值不会改变已推断类型。
- `resolve_call_detailed` 覆盖 field_map / local / this / static 四种接收者解析，
  以及 getter/setter/util 噪声跳过规则。

### L2 中层：var-resolve bag
- 用 3 个真实形状的 Java 文件（Controller + Service + VO）构建完整 `GlobalAst`，
  验证 `build_method_var_resolve_payload` 产出的 locals/receivers/call_sites/stats 全部正确。
- 这是下游 change_impact / setter 发现的**唯一数据源**，先保证它正确再谈上层。

### L3 深层：大方法切分与调用链
- `_line_brace_delta`：字符串/字符/注释/转义中的花括号不计数（变量流切分的正确性基础）。
- `_split_method_code_chunks`：长方法切分后 join 必须还原原文（空白无关比较）。
- `_entry_call_spine`：入口 → Service → Repo 的直接执行步骤，排除 off-chain 兄弟方法。

### L4 业务问答：分支后变量变化
- 合成 `DemoWithdrawalsServiceImpl` 源码：`if (!orgQuotaCheck(req)) { updateLoanFail(...); return; }`。
- 验证：fail 分支动作捕获（`updateLoanFail` + 常量 `WITHDRAWALS_FAILED`）、
  update 辅助方法里 `setLoanStatus("F")` 的 setter 值解析、pass 路径注释、
  最终渲染答案包含失败分支与具体状态写值。

### L5 代码生成：接口 IO 与外送参数
- 请求参数 → 响应参数流：`reqMap.get("memberId")` → `resp.put("loanStatus","S")` →
  `result.setResponseCode("0000")` 的完整抽取。
- `suggest_outbound_param_code`：克隆 `map.put` / DTO `set` 同行代码，
  建议把新字段以 getter 形式外送。
- `_rewrite_placeholder_field`：把 `newField`/`NEW_FIELD`/`new_field`/`setNewField`
  统一改写为业务字段名（加字段落库方案的确定性生成路径）。

### L6 全链路：补丁-编译-修复循环
- 用 fake LLM judge/repair 强制每个分支：编译失败→修复补丁→重编译→成功；
  `max_repairs=0` 时补丁失败立即终止；write_file 路径；fail action 直接失败。
- 修复动作 JSON 解析：裸 JSON / fenced ```json``` / 垃圾输入 / 非法 action 类型。

## 附录：解析层优化（测试反推）

写测试时发现「测试想断言、但解析器给不出数据」的 5 个场景，已在解析层修复：

| # | 缺口（测试暴露） | 修复前 | 修复后 |
|---|-----------------|--------|--------|
| 1 | 泛型类型参数丢失 | `List<OrderItem>` → 只留 `List` | `type_args=["OrderItem"]` 保留（`ScopedName.type_args`） |
| 2 | var + 方法返回不推断 | `var count = repo.count(o)` → `None` | 项目级 `method_returns` 表 → `int / return_type` |
| 3 | lambda 参数无类型 | `items.forEach(item -> …)` → `item: None` | 接收者泛型推导 → `OrderItem / lambda`（含 fluent 链回退） |
| 4 | 方法引用丢失 | `OrderItem::getCode` 不进入调用列表 | 提取为 `OrderItem.getCode` |
| 5 | 重赋值不追踪 | `Object target; target = repo.get(name)` → 仍 `Object` | 提升为 `Order`，记录 `reassigned_to` |

**改动位置**：`app/analysis/global_ast.py`（`ScopedName.type_args/reassigned_to`、
`_type_node_args`、`extract_method_locals` 增强、`GlobalAst.returns_for()/generic_args_for()`、
`_method_calls_in_body` 方法引用）、`app/analysis/var_resolve.py`（payload 传表 + 输出 type_args/reassigned_to）。

**回归锁定**：`tests/test_parser_optimizations.py`（14 个）。

**端到端效果**（临时项目实测 `DemoFlowService#run`）：
- `locals_typed` 9/9（此前 `count`/`item`/`x`/`code` 全为 None）
- `unknown_receivers` 0
- lambda 参数、泛型参数、重赋值目标全部带类型

> 说明：重赋值只做「向上提升」（unknown/Object → 具体类型），保持 first-declaration-wins
> 语义不变；显式声明的具体类型不会被降级。

## 附录二：确定性 SQL 元数据（Mapper XML）

**问题**：`table_field_changes`（字段改动证据）完全依赖 LLM 深析生成，Mapper XML 里
INSERT/UPDATE 的确定性列映射没有被利用——"XX接口改哪些表哪些字段"缺少硬证据。

**方案**：新增 `app/analysis/sql_meta.py`，从 MyBatis XML 的 SQL 语句确定性提取：

| 信息 | 示例 |
|------|------|
| 涉及表 | `INSERT INTO demo_b_withdrawals (...)` → `["demo_b_withdrawals"]` |
| 写入列 | `SET loan_status = #{s}, fail_reason = #{r}` → `["loan_status","fail_reason"]` |
| 读取列 | `WHERE order_id = #{oid}` → `["order_id"]` |
| 参数绑定 | `#{dealRefNo,jdbcType=VARCHAR}` → `["dealRefNo"]`（jdbcType 注解被清理） |
| JOIN 表 | `FROM a JOIN b ON ...` → `["a","b"]` |

**接入**：`global_ast._parse_one_mapper_xml` 把每语句元数据挂到
`AstType.method_sql_meta`，汇总 `sql_table_fields`（表→写入列）；
`field_evidence._load_mapper_sql_changes` 在运行时按需解析（只扫 XML，不建全量 AST），
并入 `collect_field_evidence_pack` 的 tfc 证据流（`source="mapper_xml_sql"`），
渲染时与 AI 总结分栏展示（「Mapper SQL 确定性证据」）。

**回归锁定**：`tests/test_sql_meta_cst.py`（9 个）。

## 附录三：Javadoc/注释业务描述提取

**问题**：`_heuristic_deep` 的 summary 是占位符 `"{Class}#{method} 业务节点"`，
方法上方真实存在的 Javadoc/注释没有被利用。

**方案**：新增 `app/analysis/comment_meta.py`：

- `_preceding_comment_text`：tree-sitter 前序遍历中方法声明紧邻的注释块
  （Javadoc `/** */` 或行注释 `//`，空白间隔 ≤1 行）
- `AstMethod.doc_comment` / `ParsedMethod.doc_comment`：解析期挂载
- `business_summary_from_comment`：正文行 → `summary_business_clear`
- `param_flow_from_javadoc`：`@param` → `impl_view.params`
- `_heuristic_deep` 使用注释生成专业业务摘要（无注释时回退占位符）

**效果**：`/** 查询订单详情并校验商户额度 ... */` → summary 从占位符变为真实业务句子，
`@param orderNo 订单号` → 参数说明进 `impl_view.params`。

**回归锁定**：`tests/test_comment_meta_cst.py`（11 个）。
