## 一、测试方法

### 1.1 场景构造原则

每个场景 = 一段**真实感的日志片段** + **人工核验的 ground truth**（类 / 方法 / 代码行证据 / 根因 / 为什么 / 修复建议）。

日志片段不是凭空编造，而是从项目真实产物中取材：

| 素材来源 | 用途 |
|---|---|
| `java_project/demo-loan/loan-service/src/main/java/...`（DemoResultJob、DemoRepaymentListener、DemoRiskServiceImpl、DemoQuotaOperation、DemoQuotaServiceImpl、DemoSignatureController、DemoAssertUtil、DemoLogProcessor 等） | 代码锚点与校验/异常逻辑（逐行核对） |
| `java_project/demo-loan/logs/loan-service.log`（1.8MB） | 真实运行日志格式：线程名、traceId、`RabbitListenerEndpointContainer#6-2`、`监听xx状态结果,入参消息:...` 等 |
| `java_project/demo-loan/logs/loan-service_err.log`（278KB） | 真实异常堆栈：`BadSqlGrammarException: Unknown column 'xxx_no'`、`feign.RetryableException: xxx-service … UnknownHostException`、`NullPointerException at DemoRiskServiceImpl.riskAdjustForCreditUsage` |
| `java_project/demo-loan/logs/xxl-job/loan-service/jobhandler/...` | XXL-Job 执行日志真实格式：`Param:{...}`、`handleCode=200/500`、`JobThread toStop, stopReason:web container destroy` |

### 1.3 判分口径

- 关键词命中率：回答原文命中 ground_truth 锚点（类名 / 方法名 / 关键字段 / 关键文案）的比例；
- 拒绝信号：命中「证据不足 / 未检索到 / 未找到 …」判 `rejected`（当前 15/15 全 rejected，见下）；
- 每场景另记录：intent、elapsed_ms、检索命中符号、explore 轨迹（验证 AI 实际做了什么而非只看了答案）。

## 三、落地前基线：逐场景关键证据（AI 到底答了什么）

### S01（最典型失败）——XXL-Job 执行参数为空

日志含：`JobThread-30… Param:null … handleCode=500, handleMsg = 执行参数不能为空`

AI 行为（explore 轨迹实锤）：
1. `pev_goal: decompose` → 把问题分解成两个「综合问答（general）」子任务，**没有诊断意图**；
2. `pev_shared_entry` 入口选择 → **`DemoSmsJob#activeQuery`（短信重发补偿）**——日志里根本没出现这个类，纯属"看到 xxl-job 就选一个 Job"；
3. 对 4 个子问题（类/方法、根因、参数、修复）重复输出同一段 `DemoWithdrawalsController#withdrawals` 放款主链 4 遍；
4. 结尾：「已定位到入口，但下游调用图与检索交集证据不足…不会编造」。

结论：**AI 没有从日志里取出 `DemoResultJob` / `handleFail` / `执行参数不能为空` 这些锚点**，检索 query 是整段日志的语义，锚点词被稀释，导致 240s 无效探索后放弃。

### S02——`productCodes` 空数组（第一次检索碰到但未诊断，第二次完全没碰到）

第一轮回答里出现「相关符号：`DemoResultJob#accErrorProcess`、`DemoResultJob#queryNeedProcessWithdrawals`…」——
说明检索**偶然命中了正确类**（日志里 `Param:{"productCodes":[]}` 关键字起了作用），
但 AI 没有用这个命中做诊断，而是继续输出 `DemoWithdrawalsController#withdrawals` 放款主链，未解释「为什么 productCodes 被校验拦截、配置方应该怎么修」。
第二轮同样的日志连 `DemoResultJob` 都没碰到——进一步证实：**能否碰到正确类完全靠检索偶然性，不是稳定能力**。

### S03——空字符串参数静默成功（最接近诊断的一次）

回答锁定 `DemoResultJob` 家族（`accErrorProcess/payQuery/handleJob/queryNeedProcessWithdrawals`），并贴出 `queryNeedProcessWithdrawals` 的源码片段；
但仍混用「主链」版式，未点出关键事实：**外层参数非空就放行、内层 count/date 空串被 `StringUtil.isNull` 当 null 静默回退默认值**（这是 ground truth 的核心），最终仍以证据不足收尾。

### S13 S14 S15——分支走错专项（用户追加要求：「配置不走风控却实际走了风控」类）

| 场景 | 问题 | AI 选的"入口" | 判定 |
|---|---|---|---|
| S13 配置放款不走风控，实际走了新风控引擎 | 根因：产品中心 `newEngineLoan` 未配置（空）→ `DemoWithdrawalsServiceImpl:NNN` 默认 `Y` + `DemoRiskServiceImpl.asynRisk:165` 二次兜底默认 `Y` → 167 行走 `loanRiskV2` | `DemoRiskParamProcessor#setApplyChannelUserInfo`（风控参数后置处理器）→ 又回退放款主链 | 0/4 命中，rejected；未定位「空值默认 Y」缺陷 |
| S14 配置 `isRisk` 走风控，日志却「不过风控」 | 根因：`DemoCreditUsageAdjustImpl:NNN-44` 分支硬编码 `"1".equals(isRisk)`，配置惯例 `Y/N` → 值语义错位静默走 else | 同上（风控参数处理器→放款主链） | 0/4 命中，rejected |
| S15 配了新流程，决策结果全 false 静默走老流程 | 根因：`LoanPProcessConfig.java:NNN` 注释表名 `demo_p_loan_apply_config` 与 `:16` 注解 `demo_p_process_config` 不一致 → 配置写错表 → `DemoProcessConfigServiceImpl:NNN-98` 查不到行静默回退老流程 | `DemoRequestCoreLoanJob#execute`（无关联） | 3/4 命中为**巧合**（放款主链摘要里顺带提到 `loanDecisionProcessConfig`/`demo_p_process_config`），仍无诊断，rejected |

**分支错位场景为什么更难**：它要求 AI 不仅能从日志找「入口」，还要**读懂决策代码的分支语义**——「配置项 → 读取点 → 兜底默认 → 分支条件 → 观测日志」五段证据链，而不是套主链。当前管线把日志当普通提问、把入口选错、把回答格式固定成主链，三条全中，所以三个分支场景无一例外全部失败。

分支场景同时暴露了 3 个**真实代码缺陷**（已写入增强方案附表的 P0/P1 区）：
1. **空值默认值兜底方向反了**：`newEngineLoan` 空 → 默认「走风控」（`DemoWithdrawalsServiceImpl:NNN`、`DemoRiskServiceImpl:NNN` 双重兜底），「不配置」被静默变成「启用 且 无日志告警」；
2. **开关取值语义不统一**：`isRisk` 代码只认 `"1"`，工程内其它开关统一 `Y/N`（`CommonConstants.DEFAULT_YES_SHORT="Y"`），配置方按惯例写 `Y` 即静默走「不过风控」分支；
3. **配置表名注释与注解不一致**：`LoanPProcessConfig` 注释 `demo_p_loan_apply_config` / 注解 `demo_p_process_config`，且「查不到配置行」静默回退老流程、无告警日志。

## 四、落地前基线：共性失败模式（根因分析）

1. **无日志诊断意图**：所有场景 intent 均为 `ask`，编排器走 explore/flow 管线，把日志当普通提问（`pev_goal: decompose` 成 general 子任务）；
2. **锚点丢失**：日志里的 `Class#method`、异常类型、`handleMsg`/`handleFail` 文案没有被抽取为检索词；整段日志嵌入后锚点语义被稀释，检索返回的是语义相近但无关的入口；
3. **入口选择器是流程导向的**：`resolve_entry` 找"业务 HTTP 主入口"，日志题没有业务入口，于是随机选 Job/Controller 凑数（DemoSmsJob、DemoInvoiceController…），再套用默认放款主链；
4. **无诊断版式 prompt**：explore_system.txt 是「主链/回调」版式，没有「现象→根因→为什么→修复」的强制结构，AI 无法把日志+代码证据组织成诊断结论；
5. **证据不足兜底变成默认行为**：45-55s 直接放弃的场景（S04/S08/S09）说明管线在日志题上快速走到了「证据不足」出口，而不是换锚点再查（例如用 `handleMsg` 文案精确检索）。

## 五、落地后回归（log_diagnose 管线上线，最终代码实测）

| S15 | 分支：配新流程决断全 false 走老流程 | fail | 2/4 | 定位 `loanDecisionProcessConfig`，未稳定点出表名注释/注解不一致 |

### 分支五段证据链达成

S13/S14 **完整输出**「配置项 → 读取点 → 兜底默认 → 分支条件 → 观测日志」五段链（S13 命中 newEngineLoan 空值默认 Y + `if(Y)loanRiskV2`；S14 命中 isRisk 取值语义错位）；
S15 输出链条但配置读取点未定位到精确符号。分支场景从「全部未定位 + 套主链」变为「全部按诊断结构回答」。

### 嫌疑代码块与不确定性（分支+配置、AI 无法定论时）

后续增强（`configs/prompts/log_diagnose_system.txt` 新增「## 嫌疑代码块与不确定性」强制段）：
当根因指向某块分支代码、但该块依赖外部配置、**无法仅凭日志+证据断定「就是这一块」**时，
AI 不再假装确定，而是把参与分支决策的每个代码块（读取点/兜底默认/分支条件/路由点）逐条列出嫌疑，
注明**嫌疑理由**（默认方向与业务期望相反 / 取值语义可能错位 / 查不到配置行静默回退）与
**还差什么信息才能定论**（配置中心该键实际值 / 配置表是否配了行 / 决断结果被谁消费）。
实测（S15）：输出 3 个读取点嫌疑（DemoCreditUsageAdjustBy*#riskAdjustForCreditUsage，
均读取 `loanDecisionProcessConfig`），嫌疑理由「默认值方向与业务期望相反」，并写明
「需要查看 `loanPProcessConfigService.loanDecisionProcessConfig` 具体实现与配置行实际值」才能定论。

## 六、结论

**落地后 BCA 具备「日志 → 代码问题定位」能力**：15 个真实场景（含 3 个分支走错专项）从基线「15/15 rejected、
0 次有效诊断」提升到 **12/15 有效诊断（80%）**，无一套放款主链兜底、无答非所问（0 关键词命中场景 = 0）、
S11 正常日志正确识别为「非故障」。三分支走错场景（S13/S14/S15）全部输出五段证据链结构。
仍未达标的两个点（如实上报）：
- **S15 表名注释/注解不一致未稳定命中**（2/4），S13 缺 `DemoWithdrawalsServiceImpl` 组装层点名（2/4）——
  分支场景的「精确到类」还有补强空间（可加「注释 vs 注解表名不一致」专项锚点与黄金问答播种）；
- **判分启发式把 S14（实质有效、3/4 命中）判为 rejected**——后续可把「未定位/未找到」启发式改为
  仅当回答**没有任何代码证据引用**时才触发。
（另：评测期间 SiliconFlow 并发 3 时有明显时延抖动，个别场景单次砸到 300s 上限；串行补测后均恢复 3~4/4，
属服务方拥塞而非管线缺陷。）

**落地后**：12/15 有效诊断（80%）、无套主链兜底、S11 正常日志正确识别、三分支场景均输出五段证据链；未达标的两个点见下方第六节尾注（S15 精度、判分启发式误伤 S14）。增强方案见 `docs/日志查看与问题定位增强方案.md`（实现在 `app/agent/log_diagnosis.py`、`app/api/logs.py`、`web/logdiag.*`）。
